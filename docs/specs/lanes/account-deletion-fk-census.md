# Account deletion FK census (Lane 6)

This census lists everything a plain `delete from auth.users` reaches in the Argus schema. Lane 6 ([handoff](mvee-five-lane-handoff.md#lane-6-account-deletion)) starts from it. It is the authoritative list of foreign keys for in-app account deletion and replaces the hand-read list in the handoff's "What exists today".

**Base:** `codex/private-alpha-next` at `bf6ccf85` (#788, Lane 1 backend), with all 108 migrations applied.

**Source:** two things produce it. A `pg_catalog` sweep finds every foreign key into `auth.users`, or into a table that `auth.users` reaches. A live probe then deletes a fully shared user against real PostgreSQL. Both run in [`tests/test_account_deletion_fk_census_postgres.py`](../../../tests/test_account_deletion_fk_census_postgres.py), with the sweep in [`tests/account_deletion_census.py`](../../../tests/account_deletion_census.py). CI runs them in the `guest-release-gates` real-PostgreSQL matrix. The first test fails when this document and the schema disagree, so a new migration that adds, drops or changes a key has to update the census in the same PR.

Nothing here deletes anyone. The probe runs inside a transaction that is always rolled back, and it adds no deletion command and no schema change.

## What a plain delete does today

A plain delete fails. The first error is the `retain_foreign_activity` trigger: *"surviving original owners retain canonical activity history"*. To find every later blocker, the probe lifts each one inside the rolled-back transaction and tries again. It took 21 lifts before the delete went through.

- **19 foreign keys block.** Eighteen are RESTRICT. One is NO ACTION and initially deferred, so it fires only at commit.
- **One trigger blocks:** `retain_foreign_activity` on `financial_activity_groups`.
- **One check blocks:** `households_check`. `households.admin_user_id` is ON DELETE SET NULL, but an active household must have an admin, so the SET NULL itself fails.

Eight more blocking-type keys had rows in the probes and never fired:

- **Six run between the person's own rows and go in the same cascade:** the three asset debt-link keys, `memory_records` → `memory_consent_actions` (seeded with a reconciliation still pending), `run_context_packets` → `context_packets` (from the guest probe), and the deferred `financial_activity_groups` → current revision.
- **Two restrict in the catalog, but their rows go first through another cascade:** `financial_goal_allocations.contributor_membership_id` goes through the person's own account, and `financial_plan_links` (`budget_id`, `user_id`) goes through the plan owner's `user_id`.

Lane 6 shouldn't rely on that order once it re-keys rows.

The rows B can see that a plain delete would destroy:

- **`financial_plan_links` (5).** `user_id` is the plan owner and cascades, so every claim in a shared plan the person owns goes, B's contributions included. Decision 17 step 1.2 hands those plans to the longest-standing participant. That has to happen **before** step 1.3's leave (Priya's #782 note 1), or the new owner gets a read-only archive.
- **`financial_goal_allocations` (3).** Backing from the person's accounts into B's goals cascades with the account, and so does B's backing of a goal the person owns.
- **`household_members` (2).** These cascade, but plan rows still restrict them. Step 5.1 gives the person one former-member placeholder membership per household, keyed to that household's placeholder `auth.users` row. It shows as "Former member" or "Exmiembro", in the viewer's language.
- **`household_account_grants` (4), `household_command_receipts` (7), `household_invitations` (3 set to null), `households` (1 set to null).** These are grants, idempotency receipts and invite ids. Step 1.3's leave and step 4 handle them explicitly.
- **`financial_activity_memberships` (1) and `financial_record_revisions` (1 removed, 1 set to null).** These are legs of cross-owner transfers. B's record that the person entered keeps its row, and `recorded_by` sets to null.

## What Lane 6 has to change before re-keying

Moving rows to a placeholder, or moving a plan to a new owner, means changing owner ids on keyed rows. The "Re-key to a placeholder" column says what each key needs. In short:

- **Keys straight to `auth.users`** (`financial_plan_definition_revisions.owner_id` and `actor_id`, `household_plan_receipts.actor_id`, and every `user_id` that cascades): a placeholder id has to be a real `auth.users` row, or the key has to change. `owner_id` and `household_plan_receipts.actor_id` are `not null`. `financial_plan_definition_revisions.actor_id` is nullable, so it can be set to null.
- **Composite owner keys** (`household_plan_bindings` to the plan definitions and `first_shared_revision` / `retained_revision`, `financial_plan_links`, `financial_goal_allocations` and `financial_goal_allocation_revisions` to accounts, goals and bindings, and the archive tables to `financial_activity_revisions`): every one is ON UPDATE NO ACTION and **not deferrable**. Neither side can change its owner id first. A plan transfer or a placeholder needs the keys it re-keys made `DEFERRABLE INITIALLY IMMEDIATE` in Lane 6's migration, and only those. ON UPDATE CASCADE doesn't fit: `household_plan_bindings.owner_user_id` sits in 7 composite keys and `financial_plan_links.user_id` in 5, so one cascading parent breaks the others mid-statement.
- **Membership keys** (`household_plan_participants`, `financial_plan_responsibilities`, `household_plan_receipts`, and the `contributor_membership_id` columns): these key on `household_members.id`, not on the user id. Each one is re-pointed to the person's placeholder membership in the household it belongs to. That membership is keyed to the household's placeholder `auth.users` row, never nulled: a null leaves the `(membership, household, user)` keys unchecked under MATCH SIMPLE and breaks `validate_shared_allocation_binding`.
- **Deferrable keys:** only three are deferrable, all initially deferred: `financial_activity_memberships` → `financial_record_revisions` (the record-owner key), `financial_activity_groups` → its current revision, and `financial_record_revisions` reversal → `financial_activity_revisions`. They fire only at commit. A test that rolls back without `set constraints all immediate` never sees them. **Lane 6 (`20261004090000_account_deletion.sql`)** makes the composite owner keys it re-keys `DEFERRABLE INITIALLY IMMEDIATE`, and only those; the deletion writer functions defer them inside the deletion transaction and set every constraint immediate again before they return. The tables below show them as `deferrable`.
- **ON UPDATE CASCADE:** only the two `conversation_read_states` keys use it.

### Sharing scopes and the standalone shared group

This section is the one definition of the term. Other documents link here.

A **sharing scope** is the unit that gets one placeholder per departed person. `argus_private.deletion_placeholder_units` in `20261004090000_account_deletion.sql` lists the scopes a person's rows are pinned in, and `argus_private.account_deletion_placeholders.scope_kind` records each one as `household` or `group`.

- **Household.** Every shared plan sits in a household (`household_plan_bindings.household_id` is `not null`). Each plan that holds any of the person's rows belongs to its household, every membership-keyed row to its membership's household, and every activity group that a household plan claims or archives to that plan's household. When plans in two households claim the same activity group, it belongs to the household whose claim is oldest (`argus_private.deletion_activity_household`, decision (c) below).
- **Standalone shared group.** One activity group (a `financial_activity_groups` row, such as a transfer or payment between two people's accounts) whose legs in `financial_activity_memberships` have more than one owner, and that no household plan claims or archives. "More than one owner" means either the person owns the group and another person's record is one of its legs, or another person owns it and one of the person's records is a leg. "No household plan claims or archives it" means no `financial_plan_links` row with a binding, no `household_plan_archived_claims` row and no `household_plan_archived_activities` row names it. Its scope id is the activity group's own id. It is not a household, not a plan, and not the founder's group access link.

A placeholder owns rows in exactly one scope. Decision (c) adds a reference, not ownership: when plans in two households claim one of the person's activities, the activity moves to the placeholder of the household with the oldest claim, and the other household's claims and archives on it are re-pointed to that same placeholder (`activity_owner_id`, in `argus_private.deletion_place_unit`). Those rows still belong to the other household's plan. So a placeholder can be named by rows in a second household, but it never owns rows there. The run counts those references as `counts.cross_scope_references`.

### Placeholders: one per sharing scope, none tied to the person

Decision 17 says the placeholder "has no user id, name, avatar, or email". Every key above that holds an owner id points, directly or through a composite key, at `auth.users`, so the placeholder has to be a real `auth.users` row (Priya's PG17 check). "No user id" therefore means **no id tied to the person**:

- **One placeholder per (household or standalone shared group, departed person).** A household is one sharing scope: every plan and membership-keyed row of the person inside one household re-keys to that household's single placeholder, because its members already knew it was one person. The only scope outside a household is a [standalone shared group](#sharing-scopes-and-the-standalone-shared-group), which gets its own placeholder. A placeholder owns rows in one scope only; under rule (c) below, another household's claim or archive can name it in a reference: that household can read the activity through it but cannot edit it. Each placeholder is a nameless `auth.users` row, created through the Supabase Admin API (`auth.admin.createUser`) as `exmiembro+<random uuid>@cuadrao.invalid`, email confirmed, with `app_metadata {"placeholder": true}` and `phone` null. Argus sends `user_metadata {}`; GoTrue's email confirm then writes `{"email_verified": true}` into `raw_user_meta_data` (supabase/auth `internal/models/user.go`, `Confirm`), so that flag is all the row's user metadata holds (note 8). It is banned through the same call (`ban_duration` 876000h, so GoTrue sets `banned_until` about 100 years out), and it has no password. GoTrue's admin create INSERTs the row first, with app_metadata `{"provider": "email", "providers": ["email"]}`, and only then, in the same transaction, sets the caller's app_metadata, confirms the email and sets the ban (supabase/auth `internal/api/admin.go`, `adminUserCreate`). So the auth triggers skip placeholders by the `exmiembro+…@cuadrao.invalid` email as well as by `app_metadata`, and a `refuse_placeholder_email` trigger refuses that domain to every id not registered in `argus_private.account_placeholders` (a public sign-up or an email change to it fails). GoTrue gives it one `email` identity, whose `identity_data` holds only the random email, the placeholder's own id (`sub`) and the `email_verified` and `phone_verified` flags (false). Yelena (HoE) set this on Oct 2, replacing the per-person tombstone in Marcus's design note, and refined it from per plan to per household at 11:06 PM CT, matching Maya's #796.
- **Former-member numbering stays per plan**, because it is only a label, localized to the viewer's language ("Former member" in English, "Exmiembro" in Spanish). A plan shows the bare label when it shows one former member, and "Former member 1", "Former member 2" (or "Exmiembro 1", "Exmiembro 2") when it shows several, ordered by when they left the household.
- **Nothing links back to the person.** The placeholder id is random, the email holds only another random uuid, and the auth triggers and the API's JWT check skip and reject placeholders.
- **The run record** may map the real id to its placeholders only while the run is in flight, so a retry reuses them. It keys on `subject_hash` and carries `analytics_distinct_id`; both are unsalted hashes of the user id, so they are held only while the run is in flight too. When the run completes, the user id, both hashes, the placeholder map and the revocation rows are deleted or nulled; the run keeps only its own random `id`, the status, the step outcomes (including any operator's force-complete reason) and the counts (Priya 7).
- **An activity two households' plans pin (decision c, Lucas, Oct 3).** An activity moves in place, so it can belong to one placeholder only. It goes to the placeholder of the household whose plan claim on it is oldest: the earliest claim `created_at` (a live claim, or an archived claim, which keeps its live claim's time), then the lowest claim id; an archive with no claim of its own (a refund pinned with its purchase) comes last. Lane 6's migration adds `financial_plan_links.created_at` and `household_plan_archived_claims.claim_created_at` for this; claims made before it share the migration's time and fall to the claim id. Every other household's claim or archive on that activity stays as a read-only reference that names the winning placeholder and still resolves. The run record counts them (`counts.cross_scope_references`). Priya to confirm in her eval.
- **Re-key method: move in place under `DEFERRABLE INITIALLY IMMEDIATE`, plus account copies** (not copy, re-point, delete). Lane 6's migration makes only the composite keys it re-keys deferrable. The deletion transaction defers them, moves the rows in place and checks every key at commit. Bindings, definitions and their revisions, claims and archives, and the person's activities, records and record revisions keep their ids, revision numbers and timestamps, because other owners' legs and claims name them by id (a single-leg activity even shares its record's id). Only accounts are copied under the placeholder, one copy per scope, because an account also holds rows that go with the person; the moved records point at the copy. Locked history moves only through the deletion writer functions. Deferral doesn't relax three row rules, so the move order has to satisfy them on every statement:
  - **`shared claim must retain its canonical binding`** (trigger `shared_claim_binding` on `financial_plan_links`, before insert or update): a shared claim's `user_id` must be its binding's `owner_user_id`, and its contributor membership must be in the binding's household. The binding moves first, then its claims, to the same owner.
  - **`shared allocation must retain true owner and consent`** (trigger `shared_allocation_binding` on `financial_goal_allocations`): `goal_owner_id` must be the binding owner and `account_owner_id` the user of the contributor membership. An allocation from the person's account moves to the account copy and the placeholder membership together.
  - **`financial_record_revisions.reversal_of_owner_id` is generated** from `details` (`reversal_of_owner_id`, else the row's `user_id`) and feeds the deferred reversal key to `financial_activity_revisions`. It can't be updated directly and changes only through `details`. When a record moves, the writer rewrites `details` so the generated owner still names wherever the reversed activity now lives.

## Outside the foreign keys

- **`financial_asset_changes.recorded_by`** holds a user id with no foreign key. The table has `check (recorded_by = user_id)` and cascades with its owner, and service_role can only select and insert, so it can't hold the person's id on another owner's row. Lane 6 asserts that no row holds the id. It doesn't clear anything.
- **`feedback.context` holds the account email** (`account_email`) and the user id for an account-deletion request. `feedback.user_id` is ON DELETE SET NULL, which clears only the column, so step 6 clears both from `context` explicitly, before the auth user goes.
- **No foreign key reaches these tables, so a delete leaves them alone:** `checkpoints`, `checkpoint_blobs` and `checkpoint_writes`, keyed by conversation id as text (the guest probe confirms they survive). Also `argus_memory_vectors` (`payload` jsonb), `private_alpha_allowlist` (email), `private_alpha_access_welcome_claims` and `_deliveries` (recipient email), `guest_funnel_milestones` (`subject_key`), and `visitor_usage_counters` (`visitor_key`). Lane 6 decides for each one whether it identifies the person.
- **Supabase platform schemas** (`auth`, `storage`, `realtime` and the rest) are left out of the sweep, because their keys differ between the local Supabase stack and a vanilla PostgreSQL. Since #778 the person's retained document sources are Storage objects under `{user_id}/`; the run deletes that prefix as its `storage` step, below, and again right before the auth delete. Capture refuses a person with a run in flight and removes its object.
- **Lane 1's who-invited-whom record (#788) is in.** `invite_referrals` keeps `sender_ref`, a random uuid with no foreign key. The `invite_sender_refs` row that maps the person to it cascades, so the ref left behind identifies nobody. `beta_invitations.created_by` sets to null, so the person's unused beta invites would stay live and anonymous. Lane 6's migration ships one **Household-owned** function, `argus_private.forget_invite_party`: Household owns its rules and its tests (`tests/test_household_forget_invite_party_postgres.py`), and the Household owner (Yelena, HoE) signed off on Oct 3. It revokes them and **rotates** (does not null) `sender_ref`: a distinct fresh `sender_ref` per row; `inviter_origin_id` chain unchanged (Priya, Oct 3). No value left groups the person's invites, so the per-user invite count for the deleted sender intentionally ends.
- **Apple credentials (#793, landed; revoke outcomes and `discard_unreadable` from #802).** `apple_sign_in_credentials.user_id` is ON DELETE RESTRICT to `auth.users`, so a stored Apple token blocks the account delete until it is gone. Revocation is a step in the resumable run, before step 7. The run calls #802's `revoke()`: on Apple 200 the row is deleted and the run records `apple_revoke: revoked`; on `invalid_grant` #802 deletes the row and returns `already_revoked`, which the run records as its own outcome and counts for the spike alert. Any other Apple error (for example `invalid_request` after the person revoked the app in their Apple ID settings, TN3107) leaves the row and the step pending: the account stays locked and the account delete waits. After 7 days pending the run raises an operator alert, and only an operator can force-complete the step, with a required reason kept in the run record (`force_complete_step`: a dry run unless confirmed, refused before the step has waited 7 days, and for Apple, Plaid and Gmail one more revoke is attempted and recorded before anything is dropped); there is no user-facing bypass. On `credential_unreadable` the run first checks the key (`key_check`: the token's stored key fingerprint equals this process's key's; see below). Only then does it call #802's `discard_unreadable`, which checks the same itself, and record `apple_revoke: unrecoverable`; a different or missing fingerprint, or no key, keeps the row pending (`key_unproven` / `key_unavailable`) and alerts. A person with no stored Apple credential (never captured, or a sign-in before #793) gets `apple_revoke: none`. A process with no Apple service configured fails safe: the step stays pending, it is never skipped. No token is logged. The probe world stores no Apple token, so it isn't among the blockers above; a person who signed in with Apple adds it.
- **Provider credentials, PostHog and late writes.** The data step captures every Plaid access token and Gmail refresh token into `argus_private.account_deletion_revocations` before the connections go; the run revokes each before the account delete. Outcomes: `revoked`; `already_revoked` (Google `invalid_grant`/`invalid_token`, Plaid item gone; counted per run, with a metric on each and an alert when 5 or more runs updated in the last 24 hours have seen one, any provider; #802 introduced the same handling for Apple); `unrecoverable` only when the credential was sealed under this process's key and still does not open (`key_check`: its stored key fingerprint equals the running key's); `operator_forced`. A different or missing fingerprint, or no key, keeps the row pending with its ciphertext (`key_unproven` / `key_unavailable`) and alerts: it is never taken as a dead credential. The fingerprint is `secret_key_fingerprint` (`SecretBox.key_id`: 32 hex characters of HMAC-SHA256 of a fixed label under the key, non-secret), which Lane 6's migration adds to `financial_source_connections`, `apple_sign_in_credentials` and the captured revocation row, and which every sealing path sets (Plaid link and reconnect, Gmail connect and reconnect, Apple capture). Nothing about anyone else's credentials counts: during a rolling rotation an old-key process may seal after a new-key one (Priya B1, which replaced the seal-time check of Marcus re-check S1). Credentials sealed before the migration have no fingerprint and are held until a process that can open them revokes them, or an operator forces the step after 7 days. The `storage` step (#778) deletes every retained document source under the person's Storage prefix; a Storage failure keeps it pending and the account locked, and only a successful delete completes it (no operator force). The PostHog step counts as done only on a real deletion, or on the recording fake where it is explicitly the adapter (tests, local dev); anywhere else it stays pending until the real adapter ships (#806, which blocks the Lane 6 flag). Any provider or PostHog step pending for 7 days raises an operator alert, and only an operator can force-complete it, with a required reason kept in the run record. The `storage` step is ours, so it is never forceable: after 7 days it raises its own alert to fix Storage. Right before the Admin API delete the run reads every RESTRICT or NO ACTION key to `auth.users` from the catalog (`deletion_auth_blockers`); a write that committed after the data step is scrubbed once more, and anything still holding the person keeps the run pending instead of failing the delete.
- **Invite code digests (#794, in).** `argus_private.invite_code_digests` holds the keyed HMAC-SHA-256 digest of each typed invite code and no user id. Its two CASCADE keys follow the invitation rows (see the households table): a digest goes only when its invitation row is deleted. ## Full census

Every foreign key into `auth.users`, or into a table `auth.users` reaches, grouped by area. "Plain delete, live probe" is what the probe saw:

- **Blocks:** the probe had to lift this key, with its number in the blockers list.
- **Cascades** or **sets to null:** the rows that went.
- **Inside the person's own cascade, doesn't block:** a blocking-type key whose rows went in the same delete.
- **Held:** its rows point at the person's rows that stayed, because the parent is shared or a blocker above held it.
- **Catalog only:** neither probe had rows here.

## How the probe works

The fixture reuses the Household fixtures under `tests/household/`. Their real services build:

- **Household 1:** A is admin and B is a member. Account grants run both ways.
- **Plans A owns, shared with B:** a budget, a bill, a goal and a debt. B pays into the budget, the bill and the goal, and backs A's goal from B's own account.
- **Plans B owns, shared with A:** a bill and a goal. A pays into both, backs B's goal, and carries a 50% responsibility in each.
- **A #773 archive on a plan A owns:** C joins household 1, pays into a bill A owns, and leaves.
- **Household 2:** B is admin. A joins, pays into B's bill, backs B's goal, and leaves, so departure archives pin A's activity under B's binding.
- **A's own rows:** a Plaid connection, an asset linked to one debt and then re-linked to another, a profile, a conversation and message, an account-deletion feedback row, and a full memory graph with a reconciliation still pending.

A second probe deletes a guest with the whole chat, research, route-receipt and cost-ledger graph from the guest cleanup tests. It goes through with no blocker.

The probe runs `set constraints all immediate`, deletes A, and records each error. Then it lifts that one constraint, trigger or check inside the transaction and tries again until the delete goes through. Finally it compares every table before and after, and rolls everything back.

To regenerate the rows after a migration, point `ARGUS_DISPOSABLE_DATABASE_URL` at a migrated disposable database and run `python -m tests.account_deletion_census`. It prints the sweep columns with the last two cells as `TODO`. Fill those cells in from the test's report, which it writes to `temp/account-deletion-fk-census-report.md`.
