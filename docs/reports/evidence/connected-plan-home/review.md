## Findings

1. **P1 — Normalize expectation IDs before lookup and receipt scoping.** `src/argus/domain/planning/service.py:80` (native caller: `ios/Packages/ArgusSession/Sources/ArgusSession/FinancialPlanTypes.swift:199`). Swift builds the expectation-edit path using `UUID.uuidString`, which uses uppercase hexadecimal. The route accepts a raw string, while expectation keys loaded from Postgres or created in memory are lowercase UUID strings. Thus normal native edits return AccountNotFound/404 instead of changing an expectation. Offline reproduction: create a bill; edit its uppercase ID raises AccountNotFound; edit the lowercase ID with the same body succeeds. Smallest fix: normalize/validate the expectation ID once at the service boundary before both lookup and idempotency scope construction. Add an uppercase-ID edit regression that follows the native path representation.

2. **P2 — Use the same ownership basis for projected and recorded cash.** `src/argus/domain/planning/projection.py:149-153`, in combination with the share-adjusted starting value at lines 118-120. Starting cash uses the account's ownership share, but pending movements use their entire account amounts. For a 50%-owned checking account with USD100 and a USD60 bill, the forecast shows USD50 starting, USD-10 ending and a shortfall. Recording exactly that USD60 payment changes the account to USD40, so the same projection becomes USD20 ending with no shortfall. There was no timing, amount or account change. This is reachable through existing account share controls and ordinary Plan fulfillment. Smallest fix: derive forecast positions on one consistent basis with canonical recorded position; preferably maintain projected per-account whole balances, apply the existing ownership/rounding rule to each resulting position, and aggregate their deltas. Merely rounding each individual shared movement independently can still drift from the existing once-per-account rounding contract. Add a fractional-share fulfillment continuity case and a minor-unit rounding case.

3. **P2 — Keep selected accounts removable when they become ineligible or archived.** `ios/ArgusFoundation/Plan/FinancialPlanForms.swift:131-134` (selection initialized at line 124). The selection retains all saved account IDs but renders toggles only for active cash/checking/savings accounts. Select a checking account, then change it to investment before recording activity (an allowed account edit). Its ID remains selected but the toggle disappears, so every save submits the hidden investment ID and receives account_ineligible; the user cannot repair the selection from Plan. An archived selected cash account likewise remains in the forecast but cannot be deselected. Confirmed the type-change and rejected-save sequence with the in-memory services; the hidden control follows directly from the view filter. Smallest fix: render currently selected accounts even when archived/ineligible, label their status, and allow removal while restricting new selections to eligible accounts. Preserve explicit selection rather than silently dropping IDs.
