## Retention, deletion and legal draft inputs

The legal owner must distinguish source/draft retention, chat/checkpoint retention, canonical memory and derivative index cleanup, receipts and notes, operational logs, feedback email, anonymous invitation aggregates, provider handling and backups. This audit found no basis for a new retention period, legal entity/contact, backup deletion guarantee or counsel approval.

OpenRouter's [provider logging guidance](https://openrouter.ai/docs/guides/privacy/provider-logging), reviewed October 5, says provider retention policies vary. Routing through OpenRouter does not establish zero retention. Perplexity's [privacy page](https://docs.perplexity.ai/docs/resources/privacy-security) states zero retention for Chat Completions. It does not establish the same rule for the [embeddings API](https://docs.perplexity.ai/docs/embeddings/quickstart). The `memory_embedding.py` comment that nothing is stored with the vendor is therefore not independent provider proof for embeddings. Obtain embeddings-specific terms/configuration before that claim enters a policy. Supabase's [backup documentation](https://supabase.com/docs/guides/platform/backups) describes available service behavior, not this project's inspected settings or guaranteed erasure from backups.

Decision 17 preserves former-member values/dates/category and provenance, removes receipts/photos/free-text identifying content, freezes unsettled balances outside active totals, and permits a later authorized settlement as a new event. It does not forgive or pay the balance. [Locked decision and copy](../specs/argus-decision-log.md#deleting-an-account-in-a-household) and [deletion handoff](../specs/lanes/mvee-five-lane-handoff.md#copy-founder-locked-iriss-wording) remain the owners. The trust implementation owner must reconcile the existing plan allocation/debt and space contracts before adding a frozen-balance representation. This audit does not select a substitute ledger or placeholder relationship.

At current integration, `analytics_deletion.py` keeps its recording fake restricted to explicit local/test environments. The landed `posthog_deletion.py` supplies the default-off nonlocal personless event adapter. [PostHog person docs](https://posthog.com/docs/data/persons) describe asynchronous erasure and person deletion options. The documented [event data deletion API](https://posthog.com/docs/api/data-deletion-requests) exposes request creation and status retrieval. The Alpha API requires `data_deletion:write` to submit and `data_deletion:read` to retrieve. Landed code preserves the durable submission ID and treats even a completed POST as pending. Only a later GET with matching request and submission UUIDs and completed status finishes that step. #806 owns sanitized outcome evidence; both deletion flags remain off, and real provider proof and activation remain external gates. No hosted deletion was authorized.

Apple admission fails before a run or provider side effect when a linked identity lacks a usable captured credential. Fresh-code recovery and the atomic Apple receipt permit retry without a second revocation. Account deletion remains a recoverable operation with pending/failed/operator-needed status. #807 owns the operator command and stalled-run response. The no-cron decision remains. No human operator, live alert delivery or scheduled deletion job was selected here.
